# 요구사항 분석 (적응형)

**역할 가정**: 제품 책임자

**적응형 단계**: 항상 실행됨. 상세 수준은 문제 복잡성에 따라 조정됨.

**적응형 깊이 설명은 [depth-levels.md](../common/depth-levels.md) 참조**

## 전제 조건
- 워크스페이스 감지가 완료되어야 함
- 리버스 엔지니어링이 완료되어야 함 (브라운필드인 경우)

## 실행 단계

### 단계 1: 리버스 엔지니어링 컨텍스트 로드 (가능한 경우)

**브라운필드 프로젝트인 경우**:
- `aidlc-docs/inception/reverse-engineering/architecture.md` 로드
- `aidlc-docs/inception/reverse-engineering/component-inventory.md` 로드
- `aidlc-docs/inception/reverse-engineering/technology-stack.md` 로드
- 요청 분석 시 기존 시스템 이해를 위해 사용

### 단계 2: 사용자 요청 분석 (의도 분석)

#### 2.1 요청 명확성
- **명확함**: 구체적, 잘 정의됨, 실행 가능
- **모호함**: 일반적, 애매함, 명확화 필요
- **불완전함**: 핵심 정보 누락

#### 2.2 요청 유형
- **신규 기능**: 새로운 기능 추가
- **버그 수정**: 기존 문제 수정
- **리팩터링**: 코드 구조 개선
- **업그레이드**: 의존성 또는 프레임워크 업데이트
- **마이그레이션**: 다른 기술로 이동
- **개선**: 기존 기능 향상
- **신규 프로젝트**: 처음부터 시작

#### 2.3 초기 범위 추정
- **단일 파일**: 하나의 파일 변경
- **단일 컴포넌트**: 하나의 컴포넌트/패키지 변경
- **다중 컴포넌트**: 여러 컴포넌트에 걸친 변경
- **시스템 전체**: 전체 시스템에 영향을 미치는 변경
- **시스템 간**: 여러 시스템에 영향을 미치는 변경

#### 2.4 초기 복잡성 추정
- **사소함**: 단순하고 직관적인 변경
- **단순함**: 명확한 구현 경로
- **보통**: 일부 복잡성, 여러 고려사항
- **복잡함**: 상당한 복잡성, 많은 고려사항

### 단계 3: 요구사항 깊이 결정

**요청 분석을 기반으로 깊이 결정:**

**최소 깊이** - 사용 시점:
- 요청이 명확하고 단순함
- 상세 요구사항 불필요
- 기본적인 이해만 문서화

**표준 깊이** - 사용 시점:
- 요청에 명확화 필요
- 기능 및 비기능 요구사항 필요
- 일반적인 복잡성

**포괄적 깊이** - 사용 시점:
- 여러 이해관계자가 있는 복잡한 프로젝트
- 높은 위험 또는 핵심 시스템
- 추적성이 있는 상세 요구사항 필요

### 단계 4: 현재 요구사항 평가

사용자가 제공한 내용 분석:
   - 의도 설명 또는 설명 (이미 audit.md에 기록됨)
   - 기존 요구사항 문서 (언급된 경우 워크스페이스 검색)
   - 붙여넣은 내용 또는 파일 참조
   - 비마크다운 문서를 마크다운 형식으로 변환

### 단계 5: 철저한 완전성 분석

**중요**: 포괄적인 분석을 사용하여 요구사항 완전성 평가. 모호함이나 누락된 세부사항이 있으면 기본적으로 질문.

**필수**: 이러한 모든 영역을 평가하고 불명확한 항목에 대해 질문:
- **기능 요구사항**: 핵심 기능, 사용자 상호작용, 시스템 동작
- **비기능 요구사항**: 성능, 보안, 확장성, 사용성
- **사용자 시나리오**: 사용 사례, 사용자 여정, 에지 케이스, 오류 시나리오
- **비즈니스 컨텍스트**: 목표, 제약조건, 성공 기준, 이해관계자 요구
- **기술 컨텍스트**: 통합 지점, 데이터 요구사항, 시스템 경계
- **품질 속성**: 신뢰성, 유지보수성, 테스트 가능성, 접근성

**의심스러우면 질문하세요** - 불완전한 요구사항은 나쁜 구현으로 이어집니다.

### 단계 6: 명확화 질문 생성 (선제적 접근)
   - 요구사항이 예외적으로 명확하고 완전하지 않는 한 **항상** `aidlc-docs/inception/requirements/requirement-verification-questions.md` 생성
   - 누락되거나, 불명확하거나, 모호한 영역에 대해 질문
   - 기능 요구사항, 비기능 요구사항, 사용자 시나리오, 비즈니스 컨텍스트에 집중
   - 사용자가 질문 문서에서 직접 모든 [Answer]: 태그를 채우도록 요청
   - 답변에 대한 객관식 옵션 제시 시:
     - 옵션을 A, B, C, D 등으로 라벨링
     - 옵션이 상호 배타적이고 겹치지 않도록 보장
     - 항상 사용자 정의 응답 옵션 포함: "X) 기타 (아래 [Answer]: 태그 뒤에 설명해 주세요)"
   - 문서에서 사용자 답변 대기
   - **필수**: 모든 응답에서 모호함을 분석하고 필요시 후속 질문 생성
   - **필수**: 모든 모호함이 해결되거나 사용자가 명시적으로 진행을 요청할 때까지 계속 질문

### 단계 7: 요구사항 문서 생성
   - `aidlc-docs/inception/requirements/requirements.md` 생성
   - 상단에 의도 분석 요약 포함:
     - 사용자 요청
     - 요청 유형
     - 범위 추정
     - 복잡성 추정
   - 기능 및 비기능 요구사항 모두 포함
   - 명확화 질문에 대한 사용자 답변 통합
   - 주요 요구사항의 간략한 요약 제공

### 단계 8: 상태 추적 업데이트

`aidlc-docs/aidlc-state.md` 업데이트:

```markdown
## 스테이지 진행 상황
### 🔵 INCEPTION 단계
- [x] 워크스페이스 감지
- [x] 리버스 엔지니어링 (해당되는 경우)
- [x] 요구사항 분석
```

### 단계 9: 기록 및 진행
   - 타임스탬프와 함께 `aidlc-docs/audit.md`에 승인 프롬프트 기록
   - 다음 구조로 완료 메시지 제시:
     1. **완료 알림** (필수): 항상 이것으로 시작:

```markdown
# 🔍 요구사항 분석 완료
```

     2. **AI 요약** (선택): 요구사항의 구조화된 글머리 기호 요약 제공
        - 형식: "요구사항 분석이 [프로젝트 유형/복잡성]을 식별했습니다:"
        - 주요 기능 요구사항 나열 (글머리 기호)
        - 주요 비기능 요구사항 나열 (글머리 기호)
        - 관련된 경우 아키텍처 고려사항 또는 기술 결정 언급
        - 워크플로우 지침을 포함하지 마세요 ("검토해 주세요", "알려주세요", "다음 단계로 진행", "진행하기 전에")
        - 사실적이고 내용 중심으로 유지
     3. **형식화된 워크플로우 메시지** (필수): 항상 이 정확한 형식으로 끝:

```markdown
> **📋 <u>**검토 필요:**</u>**
> 요구사항 문서를 검토해 주세요: `aidlc-docs/inception/requirements/requirements.md`



> **🚀 <u>**다음 단계?**</u>**
>
> **다음 중 선택할 수 있습니다:**
>
> 🔧 **변경 요청** - 검토를 기반으로 요구사항 수정 요청
> [사용자 스토리가 건너뛰어질 경우 이 옵션 추가:]
> 📝 **사용자 스토리 추가** - **사용자 스토리** 스테이지 포함 선택 (현재 프로젝트 단순성으로 인해 건너뛰어짐)
> ✅ **승인 및 계속** - 요구사항 승인 및 **[사용자 스토리/워크플로우 계획]**으로 진행

---
```

**참고**: 사용자 스토리 스테이지가 건너뛰어질 때만 "사용자 스토리 추가" 옵션을 포함하세요. [사용자 스토리/워크플로우 계획]을 실제 다음 스테이지 이름으로 교체하세요.

   - 진행하기 전에 명시적 사용자 승인 대기
   - 타임스탬프와 함께 승인 응답 기록
   - aidlc-state.md에서 요구사항 분석 스테이지 완료 업데이트
