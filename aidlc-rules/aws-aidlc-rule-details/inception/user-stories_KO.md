# 사용자 스토리 - 상세 단계

## 목적
**요구사항을 수락 기준이 있는 사용자 중심 스토리로 변환**

사용자 스토리는 다음에 집중합니다:
- 비즈니스 요구사항을 사용자 중심 내러티브로 번역
- 각 스토리에 대한 명확한 수락 기준 정의
- 다양한 이해관계자 유형을 대표하는 사용자 페르소나 생성
- 팀 간 공유 이해 수립
- 구현을 위한 테스트 가능한 사양 제공

## 전제 조건
- 워크스페이스 감지가 완료되어야 함
- 요구사항 분석 권장 (가능한 경우 요구사항 참조 가능)
- 워크플로우 계획이 사용자 스토리 스테이지를 실행해야 함을 표시해야 함

## 지능적 평가 가이드라인

**사용자 스토리 실행 시점**: 진행 전 이 향상된 평가 사용:

### 높은 우선순위 실행 (항상 실행)
- **새 사용자 기능**: 사용자가 직접 상호작용할 모든 새로운 기능
- **사용자 경험 변경**: 기존 사용자 워크플로우 또는 인터페이스 수정
- **다중 페르소나 시스템**: 다양한 유형의 사용자를 서비스하는 애플리케이션
- **고객 대면 API**: 외부 사용자 또는 시스템이 소비할 서비스
- **복잡한 비즈니스 로직**: 여러 시나리오 또는 비즈니스 규칙이 있는 요구사항
- **팀 간 프로젝트**: 여러 팀 간 공유 이해가 필요한 작업

### 중간 우선순위 실행 (복잡성 평가)
- **백엔드 사용자 영향**: 간접적으로 사용자 경험에 영향을 미치는 내부 변경
- **성능 개선**: 사용자에게 보이는 이점이 있는 향상
- **통합 작업**: 사용자 워크플로우에 영향을 미치는 시스템 연결
- **데이터 변경**: 사용자 데이터, 보고서 또는 분석에 영향을 미치는 수정
- **보안 향상**: 사용자 인증 또는 권한에 영향을 미치는 변경

### 복잡성 평가 요소
중간 우선순위 케이스의 경우 다음 중 하나라도 해당되면 사용자 스토리 실행:
- **범위**: 변경이 여러 컴포넌트 또는 사용자 터치포인트에 걸침
- **모호함**: 요구사항에 스토리가 명확히 할 수 있는 불명확한 측면 있음
- **위험**: 높은 비즈니스 영향 또는 오해 가능성
- **이해관계자**: 여러 비즈니스 이해관계자가 요구사항에 관여
- **테스트**: 사용자 수락 테스트가 필요함
- **옵션**: 여러 유효한 구현 접근 방식 존재

### 단순한 경우에만 건너뛰기
- **순수 리팩터링**: 사용자 영향이 전혀 없는 내부 코드 개선
- **격리된 버그 수정**: 명확한 범위의 단순하고 잘 정의된 수정
- **인프라만**: 사용자 대면 효과가 없는 변경
- **개발자 도구**: 빌드 프로세스, CI/CD 또는 개발 환경 변경
- **문서**: 기능에 영향을 미치지 않는 업데이트

### 기본 결정 규칙
**의심스러우면 사용자 스토리를 포함하고 명확화 질문을 하세요.** 적절한 명확화와 함께 포괄적인 스토리를 생성하는 오버헤드는 일반적으로 다음의 이점으로 상쇄됩니다:
- 더 명확한 요구사항 이해
- 더 나은 팀 정렬
- 개선된 테스트 기준
- 향상된 이해관계자 커뮤니케이션
- 감소된 구현 위험
- 개발 중 비용이 많이 드는 변경 감소
- 더 나은 사용자 경험 결과

# 파트 1: 계획

## 단계 1: 사용자 스토리 필요성 검증 (필수)

**중요**: 사용자 스토리를 진행하기 전에 이 평가 수행:

### 평가 프로세스
1. **요청 컨텍스트 분석**:
   - 원래 사용자 요청 및 요구사항 검토
   - 사용자 대면 vs 내부 전용 변경 식별
   - 작업의 복잡성 및 범위 평가
   - 비즈니스 이해관계자 참여 평가

2. **평가 기준 적용**:
   - 높은 우선순위 지표 확인 (항상 실행)
   - 중간 우선순위 요소 평가 (복잡성 기반 결정)
   - 건너뛰어야 하는 단순한 경우가 아닌지 확인

3. **평가 결정 문서화**:
   - `aidlc-docs/inception/plans/user-stories-assessment.md` 생성
   - 이 요청에 사용자 스토리가 가치 있는 이유에 대한 추론 포함
   - 적용되는 특정 평가 기준 참조
   - 예상 이점 설명 (명확성, 테스트, 이해관계자 정렬)

4. **정당화된 경우에만 진행**:
   - 사용자 스토리가 프로젝트에 명확한 가치를 추가해야 함
   - 평가가 구체적인 이점이 오버헤드를 상회함을 보여야 함
   - 결정이 프로젝트 이해관계자에게 방어 가능해야 함

### 평가 문서 템플릿
```markdown
# 사용자 스토리 평가

## 요청 분석
- **원래 요청**: [간략한 요약]
- **사용자 영향**: [직접/간접/없음]
- **복잡성 수준**: [단순/중간/복잡]
- **이해관계자**: [관련 당사자 나열]

## 충족된 평가 기준
- [ ] 높은 우선순위: [적용되는 기준 나열]
- [ ] 중간 우선순위: [복잡성 정당화와 함께 적용되는 기준 나열]
- [ ] 이점: [사용자 스토리에서 예상되는 가치]

## 결정
**사용자 스토리 실행**: [예/아니오]
**추론**: [상세 정당화]

## 예상 결과
- [사용자 스토리가 제공할 구체적인 이점 나열]
- [스토리가 프로젝트 성공을 어떻게 개선할지]
```

## 단계 2: 스토리 계획 생성
- 제품 책임자 역할 가정
- 스토리 개발을 위한 단계별 실행 체크리스트가 포함된 포괄적인 계획 생성
- 각 단계 및 하위 단계에 체크박스 [] 포함
- 요구사항을 사용자 스토리로 변환하는 방법론 및 접근 방식에 집중

## 단계 3: 컨텍스트에 적절한 질문 생성
**지시어**: 요구사항과 컨텍스트를 철저히 분석하여 스토리 품질 및 팀 이해를 개선할 수 있는 모든 영역을 식별합니다. 포괄적인 사용자 스토리 개발을 위해 적극적으로 질문하세요.

**중요**: 스토리 품질에 영향을 줄 수 있는 모호함이나 누락된 세부사항이 있으면 기본적으로 질문하세요. 불완전하거나 불명확한 스토리를 생성하는 것보다 너무 많은 질문을 하는 것이 낫습니다.

**질문 형식 규칙은 `common/question-format-guide.md` 참조**

- [Answer]: 태그 형식을 사용하여 질문 포함
- 모호함, 누락된 정보 또는 명확화가 필요한 모든 영역에 집중
- 사용자 입력이 스토리 생성 결정을 개선할 수 있는 곳에 질문 생성
- **의심스러우면 질문하세요** - 과신은 나쁜 스토리로 이어짐

**평가할 질문 카테고리** (모든 카테고리 고려):
- **사용자 페르소나** - 사용자 유형, 역할, 특성 및 동기에 대해 질문
- **스토리 세분성** - 적절한 상세 수준, 스토리 크기 및 분해 접근 방식에 대해 질문
- **스토리 형식** - 형식 선호도, 템플릿 사용 및 문서화 표준에 대해 질문
- **분해 접근 방식** - 구성 방법, 우선순위 지정 및 그룹화 전략에 대해 질문
- **수락 기준** - 상세 수준, 형식, 테스트 접근 방식 및 검증 방법에 대해 질문
- **사용자 여정** - 사용자 워크플로우, 상호작용 패턴 및 경험 흐름에 대해 질문
- **비즈니스 컨텍스트** - 비즈니스 목표, 성공 지표 및 이해관계자 요구에 대해 질문
- **기술 제약** - 기술 제한, 통합 요구사항 및 시스템 경계에 대해 질문

## 단계 4: 계획에 필수 스토리 산출물 포함
- **항상** 이러한 필수 산출물을 스토리 계획에 포함:
  - [ ] INVEST 기준을 따르는 사용자 스토리가 포함된 stories.md 생성
  - [ ] 사용자 아키타입 및 특성이 포함된 personas.md 생성
  - [ ] 스토리가 독립적, 협상 가능, 가치 있음, 추정 가능, 작음, 테스트 가능한지 확인
  - [ ] 각 스토리에 수락 기준 포함
  - [ ] 관련 사용자 스토리에 페르소나 매핑

## 단계 5: 스토리 옵션 제시
- 계획 문서에 스토리 분해에 대한 다양한 접근 방식 포함:
  - **사용자 여정 기반**: 스토리가 사용자 워크플로우 및 상호작용을 따름
  - **기능 기반**: 스토리가 시스템 기능 및 역량 주위로 구성됨
  - **페르소나 기반**: 스토리가 다양한 사용자 유형 및 그들의 요구에 따라 그룹화됨
  - **도메인 기반**: 스토리가 비즈니스 도메인 또는 컨텍스트 주위로 구성됨
  - **에픽 기반**: 스토리가 하위 스토리가 있는 계층적 에픽으로 구조화됨
- 각 접근 방식의 트레이드오프 및 이점 설명
- 명확한 결정 기준과 함께 하이브리드 접근 방식 허용

## 단계 6: 스토리 계획 저장
- 포함된 질문과 함께 완전한 스토리 계획을 `aidlc-docs/inception/plans/` 디렉토리에 저장
- 파일명: `story-generation-plan.md`
- 사용자 입력을 위한 모든 [Answer]: 태그 포함
- 계획이 포괄적이고 모든 스토리 개발 측면을 다루는지 확인

## 단계 7: 사용자 입력 요청
- 사용자가 스토리 계획 문서에서 직접 모든 [Answer]: 태그를 채우도록 요청
- 감사 추적 및 결정 문서화의 중요성 강조
- [Answer]: 태그를 채우는 방법에 대한 명확한 지침 제공
- 진행하기 전에 모든 질문에 답변해야 함을 설명

## 단계 8: 답변 수집
- 사용자가 문서에서 [Answer]: 태그를 사용하여 모든 질문에 답변할 때까지 대기
- 모든 [Answer]: 태그가 완료될 때까지 진행하지 않음
- 문서를 검토하여 빈 [Answer]: 태그가 없는지 확인

## 단계 9: 답변 분석 (필수)
진행하기 전에 모든 사용자 답변을 다음에 대해 신중하게 검토해야 함:
- **모호하거나 애매한 응답**: "혼합", "그 사이 어딘가", "잘 모르겠음", "상황에 따라", "아마도", "아마"
- **정의되지 않은 기준 또는 용어**: 명확한 정의 없는 개념 참조
- **모순된 답변**: 서로 충돌하는 응답
- **누락된 생성 세부사항**: 구현을 위한 구체적인 안내가 부족한 답변
- **옵션을 결합한 답변**: 명확한 결정 규칙 없이 다른 접근 방식을 병합한 응답
- **불완전한 설명**: 정의하지 않고 외부 요소를 참조하는 답변
- **가정 기반 응답**: 명시적으로 언급되지 않은 지식을 가정하는 답변

## 단계 10: 필수 후속 질문
9단계의 분석에서 모호한 답변이 발견되면 반드시:
- [Answer]: 태그를 사용하여 별도의 명확화 질문 파일 생성
- 모든 모호함이 완전히 해결될 때까지 승인으로 진행하지 않음
- **중요**: 철저히 하세요 - 모든 불명확한 응답에 대해 후속 질문
- 필요한 후속 질문 예시:
  - "'A와 B의 혼합'이라고 하셨는데 - A와 B를 언제 사용할지 결정하는 구체적인 기준은 무엇인가요?"
  - "'A와 B 사이 어딘가'라고 하셨는데 - 정확한 중간 접근 방식을 정의해 주실 수 있나요?"
  - "'잘 모르겠음'이라고 하셨는데 - 결정에 도움이 될 추가 정보는 무엇인가요?"
  - "'복잡성에 따라'라고 하셨는데 - 복잡성 수준과 임계값을 어떻게 정의하시나요?"
  - "'하이브리드 접근 방식'을 선택하셨는데 - 각 방법을 언제 사용할지에 대한 구체적인 규칙은 무엇인가요?"
  - "'아마도 X'라고 하셨는데 - 확실히 X vs 확실히 X가 아님을 결정하는 요소는 무엇인가요?"
  - "'표준 관행'을 참조하셨는데 - 그 표준 관행이 무엇인지 정의해 주실 수 있나요?"

## 단계 11: 구현 세부사항 피하기
- 우선순위 지정이나 개발 작업이 아닌 스토리 생성 방법론에 집중
- 이 단계에서 기술 생성에 대해 논의하지 않음
- 개발 일정이나 스프린트 계획 생성 피하기
- 스토리 구조 및 형식 결정에 집중 유지

## 단계 12: 승인 프롬프트 기록
