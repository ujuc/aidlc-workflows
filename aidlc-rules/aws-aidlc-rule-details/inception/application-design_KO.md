# 애플리케이션 설계 - 상세 단계

## 목적
**고수준 컴포넌트 식별 및 서비스 레이어 설계**

애플리케이션 설계는 다음에 집중합니다:
- 주요 기능 컴포넌트와 책임 식별
- 컴포넌트 인터페이스 정의 (상세 비즈니스 로직 아님)
- 오케스트레이션을 위한 서비스 레이어 설계
- 컴포넌트 의존성 및 통신 패턴 수립

**참고**: 상세 비즈니스 로직 설계는 나중에 기능 설계에서 진행 (유닛별, CONSTRUCTION 단계)

## 전제 조건
- 컨텍스트 평가가 완료되어야 함
- 요구사항 평가 권장 (기능 컨텍스트 제공)
- 스토리 개발 권장 (사용자 스토리가 설계 결정을 안내)
- 실행 계획이 애플리케이션 설계 스테이지를 실행해야 함을 표시해야 함

## 단계별 실행

### 1. 컨텍스트 분석
- `aidlc-docs/inception/requirements/requirements.md` 및 `aidlc-docs/inception/user-stories/stories.md` 읽기
- 주요 비즈니스 역량 및 기능 영역 식별
- 설계 범위 및 복잡성 결정

### 2. 애플리케이션 설계 계획 작성
- 애플리케이션 설계를 위한 체크박스 []가 포함된 계획 생성
- 컴포넌트, 책임, 메서드, 비즈니스 규칙, 서비스에 집중
- 각 단계 및 하위 단계에 체크박스 [] 포함

### 3. 계획에 필수 설계 산출물 포함
- **항상** 이러한 필수 산출물을 설계 계획에 포함:
  - [ ] 컴포넌트 정의 및 고수준 책임이 포함된 components.md 생성
  - [ ] 메서드 시그니처가 포함된 component-methods.md 생성 (비즈니스 규칙은 나중에 기능 설계에서 상세화)
  - [ ] 서비스 정의 및 오케스트레이션 패턴이 포함된 services.md 생성
  - [ ] 의존성 관계 및 통신 패턴이 포함된 component-dependency.md 생성
  - [ ] 설계 완전성 및 일관성 검증

### 4. 컨텍스트에 적절한 질문 생성
**지시어**: 요구사항과 스토리를 분석하여 이 특정 애플리케이션 설계에 관련된 질문만 생성합니다. 아래 카테고리를 영감으로 사용하고 필수 체크리스트로 사용하지 마세요. 해당되지 않으면 전체 카테고리를 건너뛰세요.

- [Answer]: 태그 형식을 사용하여 질문 포함
- 이 컨텍스트에 특정한 모호함과 누락된 정보에 집중
- 설계 결정에 사용자 입력이 필요한 경우에만 질문 생성

**예시 질문 카테고리** (필요에 따라 조정):
- **컴포넌트 식별** - 컴포넌트 경계나 구성이 불명확한 경우에만
- **컴포넌트 메서드** - 메서드 시그니처에 명확화가 필요한 경우에만 (상세 비즈니스 규칙은 나중에)
- **서비스 레이어 설계** - 서비스 오케스트레이션이나 경계가 모호한 경우에만
- **컴포넌트 의존성** - 통신 패턴이나 의존성 관리가 불명확한 경우에만
- **설계 패턴** - 아키텍처 스타일이나 패턴 선택에 사용자 입력이 필요한 경우에만

### 5. 애플리케이션 설계 계획 저장
- `aidlc-docs/inception/plans/application-design-plan.md`로 저장
- 사용자 입력을 위한 모든 [Answer]: 태그 포함
- 계획이 모든 설계 측면을 다루는지 확인

### 6. 사용자 입력 요청
- 사용자가 계획 문서에서 직접 [Answer]: 태그를 채우도록 요청
- 설계 결정의 중요성 강조
- [Answer]: 태그 완료에 대한 명확한 지침 제공

### 7. 답변 수집
- 사용자가 문서에서 [Answer]: 태그를 사용하여 모든 질문에 답변할 때까지 대기
- 모든 [Answer]: 태그가 완료될 때까지 진행하지 않음
- 문서를 검토하여 빈 [Answer]: 태그가 없는지 확인

### 8. 답변 분석 (필수)
진행하기 전에 모든 사용자 답변을 다음에 대해 신중하게 검토해야 함:
- **모호하거나 애매한 응답**: "혼합", "그 사이 어딘가", "잘 모르겠음", "상황에 따라"
- **정의되지 않은 기준 또는 용어**: 명확한 정의 없는 개념 참조
- **모순된 답변**: 서로 충돌하는 응답
- **누락된 설계 세부사항**: 구체적인 안내가 부족한 답변
- **옵션을 결합한 답변**: 명확한 결정 규칙 없이 다른 접근 방식을 병합한 응답

### 9. 필수 후속 질문
8단계의 분석에서 모호한 답변이 발견되면 반드시:
- [Answer]: 태그를 사용하여 계획 문서에 구체적인 후속 질문 추가
- 모든 모호함이 해결될 때까지 승인으로 진행하지 않음
- 필요한 후속 질문 예시:
  - "'A와 B의 혼합'이라고 하셨는데 - A와 B를 언제 사용할지 결정하는 구체적인 기준은 무엇인가요?"
  - "'A와 B 사이 어딘가'라고 하셨는데 - 정확한 중간 접근 방식을 정의해 주실 수 있나요?"
  - "'잘 모르겠음'이라고 하셨는데 - 결정에 도움이 될 추가 정보는 무엇인가요?"
  - "'복잡성에 따라'라고 하셨는데 - 복잡성 수준을 어떻게 정의하시나요?"

### 10. 애플리케이션 설계 산출물 생성
- 승인된 계획을 실행하여 설계 산출물 생성
- 다음 내용으로 `aidlc-docs/inception/application-design/components.md` 생성:
  - 컴포넌트 이름 및 목적
  - 컴포넌트 책임
  - 컴포넌트 인터페이스
- 다음 내용으로 `aidlc-docs/inception/application-design/component-methods.md` 생성:
  - 각 컴포넌트의 메서드 시그니처
  - 각 메서드의 고수준 목적
  - 입력/출력 유형
  - 참고: 상세 비즈니스 규칙은 기능 설계에서 정의됨 (유닛별, CONSTRUCTION 단계)
- 다음 내용으로 `aidlc-docs/inception/application-design/services.md` 생성:
  - 서비스 정의
  - 서비스 책임
  - 서비스 상호작용 및 오케스트레이션
- 다음 내용으로 `aidlc-docs/inception/application-design/component-dependency.md` 생성:
  - 관계를 보여주는 의존성 매트릭스
  - 컴포넌트 간 통신 패턴
  - 데이터 흐름 다이어그램

### 11. 승인 기록

### 13. 명시적 승인 대기
- 사용자가 애플리케이션 설계를 명시적으로 승인할 때까지 진행하지 않음
- 승인은 명확하고 모호하지 않아야 함
- 사용자가 변경을 요청하면 설계를 업데이트하고 승인 프로세스 반복
