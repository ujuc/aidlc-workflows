# 기능 설계

## 목적
**유닛별 상세 비즈니스 로직 설계**

기능 설계는 다음에 집중합니다:
- 유닛의 상세 비즈니스 로직 및 알고리즘
- 엔티티와 관계가 있는 도메인 모델
- 상세 비즈니스 규칙, 검증 로직 및 제약 조건
- 기술에 구애받지 않는 설계 (인프라 고려 없음)

**참고**: 이것은 애플리케이션 설계 (INCEPTION 단계)의 고수준 컴포넌트 설계를 기반으로 합니다

## 전제 조건
- 유닛 생성이 완료되어야 함
- 작업 단위 산출물이 사용 가능해야 함
- 애플리케이션 설계 권장 (고수준 컴포넌트 구조 제공)
- 실행 계획이 기능 설계 스테이지를 실행해야 함을 표시해야 함

## 개요
유닛에 대한 상세 비즈니스 로직을 설계하며, 기술에 구애받지 않고 순수하게 비즈니스 기능에 집중합니다.

## 실행 단계

### 단계 1: 유닛 컨텍스트 분석
- `aidlc-docs/inception/application-design/unit-of-work.md`에서 유닛 정의 읽기
- `aidlc-docs/inception/application-design/unit-of-work-story-map.md`에서 할당된 스토리 읽기
- 유닛 책임 및 경계 이해

### 단계 2: 기능 설계 계획 작성
- 기능 설계를 위한 체크박스 []가 포함된 계획 생성
- 비즈니스 로직, 도메인 모델, 비즈니스 규칙에 집중
- 각 단계에 체크박스 [] 포함

### 단계 3: 컨텍스트에 적절한 질문 생성
**지시어**: 유닛 정의와 기능 설계 산출물을 철저히 분석하여 기능 설계를 개선할 수 있는 모든 영역을 식별합니다. 포괄적인 이해를 위해 적극적으로 질문하세요.

**중요**: 기능 설계 품질에 영향을 줄 수 있는 모호함이나 누락된 세부사항이 있으면 기본적으로 질문하세요. 잘못된 가정을 하는 것보다 너무 많은 질문을 하는 것이 낫습니다.

- [Answer]: 태그 형식을 사용하여 질문 포함
- 모호함, 누락된 정보 또는 명확화가 필요한 모든 영역에 집중
- 사용자 입력이 기능 설계 결정을 개선할 수 있는 곳에 질문 생성
- **의심스러우면 질문하세요** - 과신은 나쁜 설계로 이어짐

**고려할 질문 카테고리** (모든 카테고리 평가):
- **비즈니스 로직 모델링** - 핵심 엔티티, 워크플로우, 데이터 변환 및 비즈니스 프로세스에 대해 질문
- **도메인 모델** - 도메인 개념, 엔티티 관계, 데이터 구조 및 비즈니스 객체에 대해 질문
- **비즈니스 규칙** - 결정 규칙, 검증 로직, 제약 조건 및 비즈니스 정책에 대해 질문
- **데이터 흐름** - 데이터 입력, 출력, 변환 및 지속성 요구사항에 대해 질문
- **통합 지점** - 외부 시스템 상호작용, API 및 데이터 교환에 대해 질문
- **오류 처리** - 오류 시나리오, 검증 실패 및 예외 처리에 대해 질문
- **비즈니스 시나리오** - 에지 케이스, 대체 흐름 및 복잡한 비즈니스 상황에 대해 질문

### 단계 4: 계획 저장
- `aidlc-docs/construction/plans/{unit-name}-functional-design-plan.md`로 저장
- 사용자 입력을 위한 모든 [Answer]: 태그 포함

### 단계 5: 답변 수집 및 분석
- 사용자가 모든 [Answer]: 태그를 완료할 때까지 대기
- **필수**: 모호하거나 불명확한 답변에 대해 모든 응답을 신중하게 검토
- **중요**: 불명확한 응답에 대해 후속 질문 추가 - 모호함과 함께 진행하지 않음
- "상황에 따라", "아마도", "잘 모르겠음", "혼합", "그 사이 어딘가" 같은 응답 찾기
- 모호함이 감지되면 명확화 질문 파일 생성
- **모든 모호함이 해결될 때까지 진행하지 않음**

### 단계 6: 기능 설계 산출물 생성
- `aidlc-docs/construction/{unit-name}/functional-design/business-logic-model.md` 생성
- `aidlc-docs/construction/{unit-name}/functional-design/business-rules.md` 생성
- `aidlc-docs/construction/{unit-name}/functional-design/domain-entities.md` 생성

### 단계 7: 완료 메시지 제시
- 다음 구조로 완료 메시지 제시:
     1. **완료 알림** (필수): 항상 이것으로 시작:

```markdown
# 기능 설계 완료 - [unit-name]
```

     2. **AI 요약** (선택): 기능 설계의 구조화된 글머리 기호 요약 제공
        - 형식: "기능 설계가 [설명]을 생성했습니다:"
        - 주요 비즈니스 로직 모델 및 엔티티 나열 (글머리 기호)
        - 정의된 비즈니스 규칙 및 검증 로직 나열
        - 도메인 모델 구조 및 관계 언급
        - 워크플로우 지침을 포함하지 마세요 ("검토해 주세요", "알려주세요", "다음 단계로 진행", "진행하기 전에")
        - 사실적이고 내용 중심으로 유지
     3. **형식화된 워크플로우 메시지** (필수): 항상 이 정확한 형식으로 끝:

```markdown
> **검토 필요:**
> 기능 설계 산출물을 검토해 주세요: `aidlc-docs/construction/[unit-name]/functional-design/`



> **다음 단계**
>
> **다음 중 선택할 수 있습니다:**
>
> **변경 요청** - 검토를 기반으로 기능 설계 수정 요청
> **다음 스테이지로 계속** - 기능 설계 승인 및 **[다음 스테이지 이름]**으로 진행

---
```

### 단계 8: 명시적 승인 대기
- 사용자가 기능 설계를 명시적으로 승인할 때까지 진행하지 않음
- 승인은 명확하고 모호하지 않아야 함
- 사용자가 변경을 요청하면 설계를 업데이트하고 승인 프로세스 반복

### 단계 9: 승인 기록 및 진행 상황 업데이트
- 타임스탬프와 함께 audit.md에 승인 기록
- 타임스탬프와 함께 사용자의 승인 응답 기록
- aidlc-state.md에서 기능 설계 스테이지 완료 표시
