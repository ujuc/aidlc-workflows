# 적응형 깊이

**목적**: AI-DLC가 문제 복잡성에 따라 상세 수준을 어떻게 적응시키는지 설명

## 핵심 원칙

**스테이지가 실행될 때 정의된 모든 산출물이 생성됩니다. "깊이"는 해당 산출물 내의 상세 수준과 엄격성을 의미하며, 이는 문제의 복잡성에 따라 적응합니다.**

## 스테이지 선택 vs 상세 수준

### 스테이지 선택 (이진)
- **워크플로우 계획**이 결정: 각 스테이지에 대해 실행 또는 건너뛰기
- **실행인 경우**: 스테이지가 실행되고 정의된 모든 산출물 생성
- **건너뛰기인 경우**: 스테이지가 전혀 실행되지 않음

### 상세 수준 (적응형)
- **단순한 문제**: 필수 세부사항만 포함된 간결한 산출물
- **복잡한 문제**: 광범위한 세부사항이 포함된 포괄적인 산출물
- **모델이 결정**: 규범적 규칙이 아닌 문제 특성에 기반

## 상세 수준에 영향을 미치는 요소

모델은 적절한 상세 수준을 결정할 때 다음 요소를 고려합니다:

1. **요청 명확성**: 사용자의 요청이 얼마나 명확하고 완전한가?
2. **문제 복잡성**: 솔루션 공간이 얼마나 복잡한가?
3. **범위**: 단일 파일, 컴포넌트, 여러 컴포넌트, 또는 시스템 전체?
4. **리스크 수준**: 오류나 누락의 영향은 무엇인가?
5. **가용 컨텍스트**: 그린필드 vs 브라운필드, 기존 문서
6. **사용자 선호도**: 사용자가 간결함 또는 상세함에 대한 선호를 표현했는가?

## 예시: 요구사항 분석 산출물

**모든 시나리오에서 동일한 산출물 생성**:
- `requirement-verification-questions.md` (필요한 경우)
- `requirements.md`

**참고**: 사용자의 초기 요청은 `audit.md`에 캡처됩니다 (별도의 user-intent.md 불필요)

**상세 수준은 복잡성에 따라 다름**:

### 단순 시나리오 (버그 수정)
- **requirement-verification-questions.md**: 필요한 명확화 질문
- **requirements.md**: 간결한 기능 요구사항, 최소한의 섹션

### 복잡한 시나리오 (시스템 마이그레이션)
- **requirement-verification-questions.md**: 여러 라운드, 10개 이상의 질문
- **requirements.md**: 포괄적인 기능 + 비기능 요구사항, 추적성, 수락 기준

## 예시: 애플리케이션 설계 산출물

**모든 시나리오에서 동일한 산출물 생성**:
- `application-design.md`
- `component-diagram.md`

**상세 수준은 복잡성에 따라 다름**:

### 단순 시나리오 (단일 컴포넌트)
- **application-design.md**: 기본 컴포넌트 설명, 주요 메서드
- **component-diagram.md**: 필수 관계만 포함된 단순 다이어그램

### 복잡한 시나리오 (다중 컴포넌트 시스템)
- **application-design.md**: 상세 컴포넌트 책임, 시그니처를 포함한 모든 메서드, 디자인 패턴, 고려된 대안
- **component-diagram.md**: 모든 관계, 데이터 흐름, 통합 지점을 포함한 포괄적인 다이어그램

## 모델을 위한 지침 원칙

**"당면한 문제에 필요한 정확한 수준의 상세함을 생성하세요 - 그 이상도 이하도 아닌."**

- 단순한 문제를 불필요한 세부사항으로 인위적으로 부풀리지 마세요
- 중요한 세부사항을 생략하여 복잡한 문제를 과소평가하지 마세요
- 문제 특성이 자연스럽게 상세 수준을 결정하도록 하세요
- 스테이지가 실행될 때 필요한 모든 산출물이 항상 생성됩니다
