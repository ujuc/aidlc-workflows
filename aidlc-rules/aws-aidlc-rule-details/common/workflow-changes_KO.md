# 워크플로우 중간 변경 및 단계 관리

## 개요

사용자는 워크플로우 중에 실행 계획이나 단계 실행의 변경을 요청할 수 있습니다. 이 문서는 이러한 요청을 안전하고 효과적으로 처리하기 위한 지침을 제공합니다.

---

## 워크플로우 중간 변경 유형

### 1. 건너뛴 단계 추가

**시나리오**: 사용자가 원래 건너뛴 단계를 추가하려고 함

**예시**: "실제로 사용자 스토리를 건너뛰었지만 추가하고 싶어요"

**처리 방법**:
1. **요청 확인**: "사용자 스토리 스테이지를 추가하려고 합니다. 이는 사용자 스토리와 페르소나를 생성합니다. 확인하시겠습니까?"
2. **의존성 확인**: 모든 전제 조건 단계가 완료되었는지 확인
3. **실행 계획 업데이트**: 근거와 함께 `execution-plan.md`에 단계 추가
4. **상태 업데이트**: `aidlc-state.md`에서 단계를 "PENDING"으로 표시
5. **단계 실행**: 일반적인 단계 실행 프로세스 따르기
6. **변경 기록**: 타임스탬프와 이유와 함께 `audit.md`에 문서화

**고려사항**:
- 새 산출물의 이점을 받을 수 있는 후속 단계를 업데이트해야 할 수 있음
- 기존 산출물이 새 정보를 통합하도록 수정이 필요할 수 있음
- 일정이 연장됨

---

### 2. 계획된 단계 건너뛰기

**시나리오**: 사용자가 실행 예정이었던 단계를 건너뛰려고 함

**예시**: "일단 NFR 설계 스테이지는 건너뛰겠습니다"

**처리 방법**:
1. **요청 확인**: "NFR 설계를 건너뛰려고 합니다. 이는 NFR 패턴이나 논리적 컴포넌트가 통합되지 않음을 의미합니다. 확인하시겠습니까?"
2. **영향에 대해 경고**: 누락될 내용과 잠재적 결과 설명
3. **명시적 확인 받기**: 사용자가 영향을 이해했음을 명시적으로 확인해야 함
4. **실행 계획 업데이트**: 이유와 함께 단계를 "SKIPPED"로 표시
5. **상태 업데이트**: `aidlc-state.md`에서 단계를 "SKIPPED"로 표시
6. **후속 단계 조정**: 후속 단계에서 수동 설정이 필요할 수 있음을 기록
7. **변경 기록**: 타임스탬프와 이유와 함께 `audit.md`에 문서화

**고려사항**:
- 후속 단계가 실패하거나 수동 개입이 필요할 수 있음
- 사용자가 누락된 산출물에 대한 책임을 수락
- 필요하면 나중에 다시 추가 가능

---

### 3. 현재 스테이지 재시작

**시나리오**: 사용자가 현재 스테이지 결과에 불만족하여 다시 하려고 함

**예시**: "이 사용자 스토리가 마음에 안 들어요. 다시 시작할 수 있나요?"

**처리 방법**:
1. **우려 사항 이해**: "스토리에서 구체적으로 무엇을 변경하고 싶으신가요?"
2. **옵션 제공**:
   - **옵션 A**: 기존 산출물 수정 (빠름, 일부 작업 보존)
   - **옵션 B**: 완전한 재시작 (백지 상태, 더 많은 시간)
3. **재시작 선택 시**:
   - 기존 산출물 아카이브: `{artifact}.backup.{timestamp}`
   - 계획 파일에서 스테이지 체크박스 재설정
   - `aidlc-state.md`에서 스테이지를 "IN PROGRESS"로 표시
   - 스테이지 완료 상태 지우기
   - 처음부터 재실행
4. **변경 기록**: 재시작 이유와 변경될 내용 문서화

**고려사항**:
- 기존 작업은 손실됨 (백업됨)
- 종속 스테이지를 다시 해야 할 수 있음
- 일정이 연장됨

---

### 4. 이전 스테이지 재시작

**시나리오**: 사용자가 완료된 스테이지로 돌아가서 다시 하려고 함

**예시**: "이전에 했던 아키텍처 결정을 변경하고 싶어요"

**처리 방법**:
1. **영향 평가**: 재시작할 스테이지에 의존하는 모든 스테이지 식별
2. **사용자에게 경고**: "애플리케이션 설계를 재시작하면 다음을 다시 해야 합니다: 유닛 계획, 유닛 생성, 유닛별 설계 (모든 유닛), 코드 계획, 코드 생성. 확인하시겠습니까?"
3. **명시적 확인 받기**: 사용자가 전체 영향을 이해해야 함
4. **확인된 경우**:
   - 영향받는 모든 산출물 아카이브
   - `aidlc-state.md`에서 영향받는 모든 스테이지 재설정
   - 영향받는 모든 계획 파일의 체크박스 지우기
   - 재시작할 스테이지로 돌아감
   - 그 지점부터 다시 실행
5. **변경 기록**: 전체 영향과 재시작 이유 문서화

**고려사항**:
- 상당한 재작업 필요
- 모든 종속 스테이지를 다시 해야 함
- 일정이 상당히 연장됨
- 재시작보다 수정이 나은지 고려

---

### 5. 스테이지 깊이 변경

**시나리오**: 사용자가 현재 또는 예정된 스테이지의 깊이 수준을 변경하려고 함

**예시**: "표준 대신 포괄적인 요구사항 분석을 하겠습니다"

**처리 방법**:
1. **요청 확인**: "요구사항 분석을 표준에서 포괄적 깊이로 변경하려고 합니다. 더 철저하지만 더 오래 걸립니다. 확인하시겠습니까?"
2. **실행 계획 업데이트**: `workflow-planning.md`에서 깊이 수준 변경
3. **접근 방식 조정**: 스테이지에 대한 포괄적 깊이 가이드라인 따르기
4. **예상 업데이트**: 새로운 일정 예상을 사용자에게 알림
5. **변경 기록**: 깊이 변경과 이유 문서화

**고려사항**:
- 더 깊음 = 더 많은 시간이지만 더 나은 품질
- 더 얕음 = 더 빠르지만 세부사항을 놓칠 수 있음
- 스테이지 전이나 중에만 변경 가능, 완료 후에는 불가

---

### 6. 워크플로우 일시 중지

**시나리오**: 사용자가 일시 중지하고 나중에 재개해야 함

**예시**: "지금은 멈추고 내일 계속해야 합니다"

**처리 방법**:
1. **현재 단계 완료**: 가능하면 진행 중인 현재 단계 완료
2. **체크박스 업데이트**: 완료된 모든 단계를 [x]로 표시
3. **상태 업데이트**: `aidlc-state.md`가 현재 상태를 반영하는지 확인
4. **일시 중지 기록**: `audit.md`에 일시 중지 지점 문서화
5. **재개 지침 제공**: "돌아오시면 기존 프로젝트를 감지하고 다음에서 계속할 것을 제안합니다: [현재 단계, 현재 스텝]"

**재개 시**:
1. **기존 프로젝트 감지**: `aidlc-state.md` 확인
2. **컨텍스트 로드**: 완료된 스테이지의 모든 산출물 읽기
3. **상태 표시**: 현재 스테이지와 다음 스텝 표시
4. **옵션 제공**: 중단한 곳에서 계속하거나 이전 작업 검토
5. **재개 기록**: `audit.md`에 재개 지점 문서화

---

### 7. 아키텍처 결정 변경

**시나리오**: 사용자가 모놀리스에서 마이크로서비스로 (또는 그 반대로) 변경하려고 함

**예시**: "실제로 모놀리스 대신 마이크로서비스로 하겠습니다"

**처리 방법**:
1. **현재 진행 상황 평가**: 워크플로우에서 얼마나 진행되었는지 결정
2. **영향 설명**:
   - 유닛 계획 전: 최소 영향, 결정만 업데이트
   - 유닛 계획 후: 유닛 계획, 유닛 생성, 모든 유닛별 설계를 다시 해야 함
   - 코드 생성 후: 상당한 재작업 필요
3. **접근 방식 권장**:
   - 워크플로우 초기: 애플리케이션 설계 스테이지부터 재시작
   - 워크플로우 후기: 수정이 가능한지 vs. 재시작 고려
4. **확인 받기**: 사용자가 변경의 전체 범위를 이해해야 함
5. **변경 실행**: 영향받는 스테이지에 대한 재시작 절차 따르기

**고려사항**:
- 아키텍처 변경은 연쇄적 영향이 있음
- 워크플로우 초기 = 변경하기 쉬움
- 워크플로우 후기 = 비용 vs. 이점 고려

---

### 8. 유닛 추가/제거

**시나리오**: 사용자가 유닛 생성 후 유닛을 추가하거나 제거하려고 함

**예시**: "결제 유닛을 결제와 청구로 분할해야 합니다"

**처리 방법**:
1. **영향 평가**: 어떤 유닛이 설계/코드를 완료했는지 결정
2. **결과 설명**:
   - 유닛 추가: 새 유닛에 대한 전체 설계와 코드 필요
   - 유닛 제거: 기능을 다른 유닛으로 재분배 필요
   - 유닛 분할: 결과 유닛 모두에 대해 설계와 코드 다시 필요
3. **유닛 산출물 업데이트**:
   - `unit-of-work.md` 수정
   - `unit-of-work-dependency.md` 업데이트
   - `unit-of-work-story-map.md` 수정
4. **영향받는 유닛 재설정**: 영향받는 유닛을 재설계 필요로 표시
5. **변경 실행**: 영향받는 유닛에 대해 일반적인 유닛 설계 및 코드 프로세스 따르기

**고려사항**:
- 해당 유닛의 모든 후속 스테이지에 영향
- 의존성이 변경되면 다른 유닛에도 영향을 줄 수 있음
- 일정 영향은 영향받는 유닛 수에 따라 다름

## 변경 처리를 위한 일반 가이드라인

### 변경하기 전

1. **요청 이해**: 사용자가 무엇을 왜 변경하려는지에 대해 명확화 질문하기
2. **영향 평가**: 영향받는 모든 스테이지, 산출물 및 의존성 식별
3. **결과 설명**: 다시 해야 할 것과 일정 영향을 명확히 전달
4. **대안 제공**: 때때로 수정이 재시작보다 나음
5. **명시적 확인 받기**: 사용자가 영향을 이해하고 수락해야 함

### 변경 중

1. **기존 작업 아카이브**: 파괴적 변경 전에 항상 백업
2. **모든 추적 업데이트**: `aidlc-state.md`, 계획 파일, `audit.md`를 동기화 유지
3. **진행 상황 전달**: 무슨 일이 일어나고 있는지 사용자에게 계속 알림
4. **변경 검증**: 모든 산출물에서 변경이 일관성 있는지 확인
5. **연속성 테스트**: 변경 후 워크플로우가 원활하게 계속될 수 있는지 확인

### 변경 후

1. **일관성 확인**: 모든 산출물이 변경과 일치하는지 확인
2. **문서 업데이트**: 모든 참조가 업데이트되었는지 확인
3. **완전히 기록**: `audit.md`에 전체 변경 이력 문서화
4. **사용자와 확인**: 변경이 사용자의 기대를 충족하는지 확인
5. **워크플로우 재개**: 새로운 상태에서 정상 실행 계속

## 변경 요청 결정 트리

```
사용자가 변경 요청
    |
    ├─ 현재 단계인가?
    |   ├─ 예: 현재 단계를 수정하거나 재시작 가능
    |   └─ 아니오: 다음 질문으로
    |
    ├─ 완료된 단계인가?
    |   ├─ 예: 종속 단계에 대한 영향 평가
    |   |   ├─ 낮은 영향: 수정하고 종속 항목 업데이트
    |   |   └─ 높은 영향: 해당 단계부터 재시작 권장
    |   └─ 아니오: 다음 질문으로
    |
    ├─ 건너뛴 단계를 추가하는 것인가?
    |   ├─ 예: 전제 조건 확인, 계획에 추가, 실행
    |   └─ 아니오: 다음 질문으로
    |
    ├─ 계획된 단계를 건너뛰는 것인가?
    |   ├─ 예: 영향에 대해 경고, 확인 받기, 건너뛰기
    |   └─ 아니오: 다음 질문으로
    |
    └─ 깊이 수준을 변경하는 것인가?
        ├─ 예: 계획 업데이트, 접근 방식 조정
        └─ 아니오: 사용자와 요청 명확화
```

## 모범 사례

1. **항상 확인**: 명시적 사용자 확인 없이 파괴적 변경을 절대 하지 마세요
2. **영향 설명**: 사용자가 결정하기 전에 결과를 이해해야 함
3. **옵션 제공**: 때때로 변경을 처리하는 여러 방법이 있음
4. **먼저 아카이브**: 파괴적 변경 전에 항상 백업
5. **모든 것 업데이트**: 모든 추적 파일을 동기화 유지
6. **철저히 기록**: 감사 추적을 위해 모든 변경 문서화
7. **이후 검증**: 워크플로우가 원활하게 계속될 수 있는지 확인
8. **유연하게**: 워크플로우는 사용자 요구에 적응해야 하며, 엄격한 프로세스를 강요하지 않음
